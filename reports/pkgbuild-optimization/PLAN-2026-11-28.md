## 2. 已确认问题与证据

### P0 — ffmpeg-full 的重复重建由外部 AUR SONAME 未登记触发

**证据**
- 当前 `packages/ffmpeg-full/PKGBUILD` 为 FFmpeg `9.1-1.9`，不是 FFmpeg 上游一天发布多次。
- Git 历史显示 2026-11-24/25 连续出现 `pkgrel 1.6 → 1.7 → 1.8 → 1.9` 的回写提交。
- GitHub Actions 2026-11-25 ABI 检测日志明确报告：`STALE ffmpeg-full -> ELF NEEDED no longer provided: libastcenc-sse2-shared.so`，随后 dispatch `ffmpeg-full`，构建环境设置 `BUMP_PKGREL=true`。
- 当前 `ffmpeg-full` 的 `.BUILDINFO` 记录依赖 `astc-encoder-5.7.1-1`；本机 `pacman -Qm astc-encoder` 确认它是外部/AUR 构建包，不属于配置的官方二进制仓库。
- `libavcodec.so.63.24.100` 的真实 `DT_NEEDED` 确实包含 `libastcenc-sse2-shared.so`。
- `packages/ffmpeg-full/.rebuild-on` 当前不存在。SONAME 检测器只从已配置仓库文件清单、已发布包和容器系统目录构建 provider 集合；外部 AUR provider 未登记时会被当成缺失。
- ABI 规则允许真实 SONAME 故障绕过 24 小时成功冷却。因此同一个未登记 SONAME 每次扫描都会再次触发重建，冷却无法解决根因。

**判断**：这是当前 ffmpeg-full 高频升级的主要已确认根因。它不是单纯的 FFmpeg 版本更新，也不是应当通过延长冷却时间掩盖的问题。

**实施**
1. 为 ffmpeg-full 增加逐包外部 SONAME 声明：`soname libastcenc-sse2-shared.so astc-encoder`。
2. 保留 `--require-needed` 校验，确保声明必须与真实产物的 DT_NEEDED 相符；不得添加全局白名单。
3. 补齐外部/AUR 依赖版本追踪：当前 `check-dependency-drift.sh` 的 `current_version()` 只查 `pacman -Si`，对容器仓库无法解析的 AUR 依赖只能计入 unresolved，不能准确比较 AUR 当前 pkgver。实现受限、可缓存、带超时/重试的 AUR RPC 版本查询；查询失败必须显示 unresolved，不能误报为已同步。
4. 为重复 SONAME 故障增加“重建后仍未解决”的状态：若一次成功发布后，包的 DT_NEEDED 与 provider 集合均未变化，不应每两小时无条件重复构建；保留真正 provider 变化或 artifact 变化时重新评估的通道。
5. `pacman -Fy` 文件数据库刷新失败时，SONAME 检测必须明确标记扫描不完整并停止自动 dispatch，不能用旧文件数据库给出可信的缺失结论。
6. 新增回归测试：AUR 外部 provider 已声明时不再 STALE；声明过期时失败；AUR 版本变化触发定点重建；provider 查询失败不等于 provider 不存在。

**验收**
- 连续执行 ABI watch 两轮，ffmpeg-full 不再因为已登记的 astc-encoder SONAME 被判 STALE。
- astc-encoder 的 pkgver 真正变化时，ffmpeg-full 能被检测为需要重建。
- 同一 SONAME 故障在成功重建后未发生变化时，不产生重复无效构建。
- 真实 SONAME 破坏仍可及时触发，不削弱 ABI 安全性。

### P1 — upstream-check 将 vendored 依赖错误派发给 AUR sync

**证据**
- `packages/ffmpeg-full/.nvchecker.toml` 除 FFmpeg 外，还追踪 vendored 的 `lensfun-master` 和 `whisper-cpp`。
- `upstream-check.yml` 的滞后升级逻辑把报告中的 package 名称直接传给 `sync.yml -f packages=$package`。
- `whisper-cpp` 是 ffmpeg-full 内部 vendored 依赖，不是 `packages/whisper-cpp` AUR 包，也没有 `.aur-url`。
- GitHub Actions run `45849329250`（2026-11-26）实际失败，日志为：`whisper-cpp is not AUR-managed (.aur-url missing).`
- 这说明上游版本检测虽能发现 vendored 依赖变化，但自动修复路由并不理解它属于 vendored pin，而是错误地交给 AUR 同步工作流。

**实施**
1. 建立唯一的更新路由解析：AUR mirror → `sync.yml`；专属 workflow 包 → 对应 updater；vendored pin/pkgvar → vendored 更新流程或明确的人工审核 issue；manual → 仅提醒，不派发 AUR sync。
2. `upstream-check.yml` 只对真正有 `.aur-url` 的包调用 `sync.yml`。不能把 nvchecker section 名称直接当作 package directory。
3. 为 `lensfun-master`、`whisper-cpp` 明确更新策略：检查上游 commit/tag、更新 pin/PKGBUILD、生成 .SRCINFO、构建候选包、功能矩阵验证，再提交并派发构建。
4. 增加路由测试，覆盖 AUR 包、workflow 包、vendored pin、manual 包和未知来源；未知来源应停止并产生可读 issue，而不是调用错误 workflow。

**验收**
- `whisper-cpp` / `lensfun-master` 的上游更新不再触发 `sync.yml` 的 .aur-url 错误。
- 每一种 update source 都能路由到唯一且正确的处理流程。
- 更新检测成功但消费失败时，issue 保持打开并显示阻塞原因。

### P1 — dsh 更新已修复，但 GitHub schedule 不是严格的两小时轮询

**现状**
- 旧问题是 updater 的 tag 正则未识别 alpha 版本，导致上游已有 `0.2.3alpha1/alpha2` 时仍停留在旧 rc；修复已合入。
- 当前只读 dry-run 已确认上游最新可打包版本为 `0.2.3alpha2`，与 PKGBUILD、.SRCINFO 和 checksum 一致。
- 16 个 updater 单元测试全部通过。
- 虽然 workflow 配置每两小时运行，但最近实际 schedule 记录间隔约 8–10 小时。这是 GitHub scheduled workflow 的 best-effort 投递行为，cron 表达式本身不保证每两小时准时执行。

**实施**
1. 保留现有 release/tag/asset/digest/PKGBUILD/.SRCINFO/候选构建校验，不降低验证标准。
2. 增加独立的 stale-age watchdog：检查上游最新可打包 release 是否高于仓库 pin；超过设定时间未消费时创建/更新 issue。
3. 在 issue 中区分“没有新版本”“上游已有新版本但工作流尚未运行”“更新器失败”“候选构建失败”“构建已完成但发布未完成”。
4. watchdog 不得只依赖同一条 dsh schedule；可复用每日 upstream-check，但必须保留明确的最后成功检查时间和告警状态。

**验收**
- 当前 `0.2.3alpha2` 不产生虚假更新。
- 模拟新 alpha/beta/rc/stable tag 时，检测器正确选中最新带 x86_64 Arch asset 的 release。
- 模拟 schedule 长时间未运行时，watchdog 能产生告警。

### P2 — 依赖与 ABI 检测的可观测性和去重

1. 将“缺少 provider”“provider 数据库未刷新”“AUR provider 未登记”“重建后仍未解决”分成不同状态，不能全部归为 STALE。
2. 每次 dispatch 记录触发源、具体依赖/SONAME、旧版本、新版本、是否绕过冷却、上次构建结果。
3. 将连续相同原因的重复 dispatch 聚合到一个 issue，保留第一次发现时间、最近确认时间和重建次数。
4. 对 dispatch 竞争窗口增加定点防重：避免两个 detector 同时读取到无活跃构建状态后重复派发；不要贸然给整个 build.yml 加全局 concurrency，以免 push 全量构建与定点重建互相阻塞。
5. 保持 pkgrel-only 不触发、binary-repack/data 等上游、真正 SONAME 破坏可紧急重建的现有语义。

### P2 — AUR 同步与 vendored 依赖边界

1. 明确区分 AUR 包自身的更新与 AUR 包依赖的更新；vendored 依赖不能伪装成 AUR package directory。
2. 对外部依赖的版本、来源、缓存时间和解析状态形成报告。
3. 对 AUR RPC 失败、限流和 404 做分类：临时失败重试，确定不存在则保持 unresolved，不得静默跳过。
4. 保留当前逐包隔离和失败包回滚机制；同步成功的包继续提交/构建，失败包保留 issue。
5. 对最近一次 sync 失败（`whisper-cpp` 路由错误）增加专项回归测试。

## 4. 实施约束

- 优先复用成熟工具与现有架构，不重写已经正常工作的构建系统。
- 先补测试和可观测性，再修改自动化路由；每个阶段独立验收。
- 不降低 checksum、签名、PKGBUILD/.SRCINFO、runtime、ELF、发布闸门要求。
- 不因减少构建次数而关闭真实 ABI/SONAME 故障检测。
- 不清理或覆盖 `dist/`、`localrepo/`、缓存和历史报告，除非先确认它们不是用户保留的本地数据。
- 不执行无关的 git reset/checkout/clean/stash/rebase/commit/push；提交和推送另行确认。
- 每阶段完成后运行对应单元测试、`tests/run-all.sh --fast`、`scripts/run-static-checks.sh`，必要时执行真实候选构建与发布后验证。
